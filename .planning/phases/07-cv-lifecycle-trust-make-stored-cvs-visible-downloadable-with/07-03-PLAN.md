<objective>
Build the write-side contract for full parsed-field editing: schema, action,
DB helper, and a permanent guard on the embedding-invalidation contract.

Purpose: `/candidates/[id]/edit` covers exactly 8 basic fields today. There is
NO edit path anywhere for work_experience, education, skills, sector_tags,
seniority_level, years_experience, the two salary fields, headline or about —
so a wrong AI-accepted value is permanently uncorrectable in-UI. This plan
lands the contracts; plan 07-04 builds the form against them. Implements D-03
(write half) and preserves D-06/D-08.

Output: A widened edit schema + action + `UpdateCandidateInput`, plus the
contract test that keeps the embed/trigger sync honest.

<interfaces>
THE CENTRAL FINDING OF THIS PHASE — verified, and the reason no app-side
invalidation code is written here.

The `invalidate_candidate_embedding` BEFORE UPDATE trigger
(migration 20260519092951:38-63) NULLs candidate_embedding + embedded_at when
any of these change:
  current_role_title, current_company, skills, seniority_level,
  years_experience, sector_tags, location, full_name

`CandidateEmbedFields` (src/lib/ai/embed-text.ts:28-38), the exact input set of
candidateEmbeddingText, is:
  full_name, current_role_title, current_company, location, skills,
  seniority_level, years_experience, sector_tags

These two sets are IDENTICAL. Therefore:
  * The search-relevant fields this plan makes editable (skills, sector_tags,
    seniority_level, years_experience) are ALREADY covered — a plain UPDATE
    fires the trigger and embed-batch re-embeds on its next 10-minute sweep.
    Writing an app-side NULL-out would be redundant.
  * The non-search fields this plan makes editable (salary_current_estimate,
    salary_expectation, headline, about, work_experience, education) are NOT in
    candidateEmbeddingText, so editing them produces a byte-identical embedding
    input. Invalidating on those would buy a Voyage call for an identical
    vector — real spend against the org AI budget for zero benefit. Do NOT
    invalidate on them.
The correct implementation is therefore ZERO invalidation code plus the Task 3
contract test that fails loudly if the two lists ever drift.

Do NOT touch src/lib/ai/profile-completeness.ts. Its comment block (lines
56-64) records the re-review V1 lesson that its predicate is deliberately NOT
unified with the reconciler's HEAL_SIGNAL_COLUMNS. Nothing in this plan needs
that predicate; leave the divergence rationale intact.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → updateCandidateAction | Recruiter-supplied patch for every parsed field, including two jsonb arrays |
| action → Postgres | Free text pasted from CVs reaches `text`, `text[]` and `jsonb` columns |
| edit write → embedding pipeline | The UPDATE decides whether an org pays for a re-embed |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-10 | Tampering | jsonb array payloads | mitigate | Zod-validate every row shape before the write; drop rows missing their required key rather than storing a malformed element the RSC parsers at page.tsx:88-120 would silently discard |
| T-07-11 | Denial of service | Postgres-illegal text | mitigate | `sanitiseForPostgres` over the whole patch at the DB boundary — the same choke point Phase 6 added to the two sibling write paths |
| T-07-12 | Elevation of privilege | cross-tenant candidate id | mitigate | RLS update policy on `candidates` is the authority; `updateCandidate` never accepts an organization_id from the caller (existing contract, unchanged) |
| T-07-13 | Denial of service | unbounded free text | mitigate | Length caps in the schema (headline 300, about 5000, tag entries 100) so a paste cannot bloat the row or the embedding input |
| T-07-14 | Information disclosure | Sentry on write failure | mitigate | `updateCandidate` already captures the PostgREST error object only, never the patch values; do not add value-bearing tags |
| T-07-15 | Tampering | npm/pip/cargo installs | accept | This plan adds NO dependencies; nothing to audit |
</threat_model>
