<interfaces>
THE DESIGN RULE FOR THIS PLAN: write NO scoring logic. `score-application-match`
already carries every guard this backfill needs, and duplicating any of them
would create a second place for them to drift.

From src/lib/inngest/enqueue-match-score.ts:
  export async function enqueueApplicationMatchScore(args: {
    organizationId: string; applicationId: string; candidateId: string;
    jobId: string | null; userId: string | null;
  }): Promise<void>
  Never throws. No-ops when jobId is null (floats). Sends
  `application/score-match` with dedup id
  `score-match:{candidateId}:{jobId}:{hourBucket}` — Inngest dedups on id for
  24h, hour-bucketed so a transient skip is never a 24h blind spot.

Guards ALREADY enforced inside score-application-match (do not re-implement):
  * tenant boundary re-check of BOTH parents against the claimed org, before
    any spend — the only barrier under service-role (lines 149-154)
  * empty-profile skip via the shared isProfileEffectivelyEmpty (line 190)
  * idempotency: version-exact cached-summary lookup short-circuits with
    `skipped: 'cached'` and zero spend (lines 202-213)
  * month-to-date spend ceiling (env.MAX_MONTHLY_MATCH_SPEND_PENCE)
  * CapExceededError handling on the org AI budget
  * ai_summaries unique constraint as the concurrent-double-fire backstop

Sweep-function shape to mirror — reconcile-cv-parses.ts is the reference for a
multi-tenant sweep in this codebase: createServiceClient() inside each
step.run, a hard row cap, per-row try/catch so one bad row never aborts the
sweep, PII-free Sentry with ids and counts only.

From src/lib/admin/guard.ts:
  export async function requireSuperAdmin(): Promise<SuperAdminUser>
From src/app/admin/actions.ts:
  export type AdminActionResult = { ok: true; message: string } | { ok: false; error: string }
  Every action in that file calls requireSuperAdmin() FIRST, before touching
  createServiceClient() (see its header comment, lines 7-11).

Relevant columns: applications has organization_id, candidate_id, job_id
(nullable by design — floats), created_at. ai_summaries carries candidate_id,
job_id, organization_id and the two embedding_version columns.

  <behavior>
    - applications with job_id null (floats) are never enqueued
    - an application whose (candidate_id, job_id) pair already has ANY ai_summaries row is skipped
    - remaining applications are enqueued oldest-first, one enqueueApplicationMatchScore call each
    - the sweep stops at the row cap and reports that it was capped rather than silently truncating
    - an event payload carrying organization_id restricts the sweep to that org
    - an event with no organization_id sweeps all orgs
    - a single row that throws does not abort the sweep
  </behavior>
  <action>
    Create the Inngest function `backfillApplicationMatchScores`, id
    'backfill-application-match-scores', triggered ONLY by the event
    'application/backfill-scores'. No cron — this is a deliberate one-off the
    founder starts, so spend never happens on a schedule nobody asked for.
    concurrency { limit: 1 }, retries 1. Carry the same `timeouts` treatment
    plan 07-05 applies to the other concurrency-1 functions (start '5m',
    finish '10m') so this sweep can never become the next thing that wedges
    the queue.

    One step.run. Inside it: createServiceClient(); select applications where
    job_id is not null, ordered created_at ascending, limited to a
    BACKFILL_ROW_CAP constant of 500, scoped to event.data.organization_id when
    present. Then read the ai_summaries rows for the selected
    (candidate_id, job_id) pairs and build a Set of already-summarised pairs.

    Use a COARSE "any summary exists for this pair" pre-filter, not a
    version-exact one, and comment why: D-04 says NO auto-rescore loops beyond
    what exists, so a pair that already has a score — even a stale-version one
    — must be left alone. The version-exact decision stays where it already
    lives, inside the scorer's own cache lookup, which is the second and
    authoritative guard.

    For each remaining row call enqueueApplicationMatchScore with the row's
    organization_id, id, candidate_id, job_id and userId null. Wrap each call
    in its own try/catch. Count enqueued, skipped-already-scored and errored,
    and return those counts. When the selection hit the cap, include a
    `truncated: true` flag in the return and Sentry-capture a warning — mirror
    the STUCK_EVENT_SWEEP_CAP treatment in stripe-reconcile.ts so a truncation
    can never lie by omission. Ids and counts only in Sentry; no PII.

    Do NOT call scoreCandidateForJob, checkCap, getMatchSummary or
    isProfileEffectivelyEmpty here. Every one of those decisions belongs to
    score-application-match and re-implementing any of them creates a second

    Write the vitest unit test with the Supabase client and
