<objective>
Design and build the one standard, tenant-branded CV template: a clean,
professional A4 layout filled deterministically from `BrandedCvData`, branded
with the org's `brand_primary`/`brand_secondary` and uploaded logo, and proven
by extracting the text back out of the generated PDF.

Purpose: this document is the phase's actual deliverable — the thing a client
receives with the agency's name on it. BCV-02 defines its sections; BCV-03
defines what it must never contain. Everything else in Phase 8 is plumbing
around this file.
Output: a pure render function (`data + branding → Buffer`) with no database,
network or auth concerns, plus sample PDFs for founder eyeball.

## Visual acceptance criteria (no UI-SPEC.md — this list IS the spec)

The anchor customer's logo is a landscape lockup (~3:2): a circled "SC"
monogram above a serif "Steele Charles" wordmark, single deep bottle/forest
green on a WHITE background with NO transparency. The template must therefore:

1. **A4 portrait**, ~40pt page margins, single column with a light rule under
   the header. Body ~10pt, section headings ~11pt bold small-caps-ish tracking.
2. **Header on a WHITE / very light area.** Never a full-bleed coloured header
   band: a non-transparent logo would be framed in an ugly white box inside it.
3. **Wide logo slot.** Reserve a landscape box (approximately 160×54pt) with
   `objectFit: 'contain'`, left-aligned, so a 3:2 lockup renders at natural
   proportions and a square mark still fits. Never stretch.
4. **No logo → deliberate fallback**: the org name as a wordmark in
   `brand_primary`, same position and weight, so the header reads as designed
   rather than empty.
5. **`brand_primary` on ACCENTS ONLY** — section heading text, the header rule,
   skill-chip borders/text, the footer rule. `brand_secondary` for one
   secondary accent (e.g. the skill-chip background tint at low opacity). No
   large filled colour areas, no white-on-colour text: a deep bottle green
   must look intentional and print cleanly on a mono printer.
6. **Sections in this order** (each omitted entirely when it has no content —
   never an empty heading): identity header (name, then headline, then a
   context line of current role · company · seniority · years · location);
   Profile (`about`); Skills; Experience (`work`); Education (`sectorTags`
   optional, rendered as a small "Sectors" line under Skills if present).
7. **Footer on every page**: `{org name}` on the left, `Page N of M` on the
   right, plus the line "Candidate contact details available from {org name}."
   — which states the contact-strip as a professional convention rather than
   leaving a client wondering.
8. **£ and diacritics render as glyphs**, guaranteed by the vendored family
   from 08-02, and text wraps rather than hyphenating mid-word.
9. **Colour safety**: run both hex values through `safeHex` from
   `src/lib/branding/colours.ts` before use, so a rogue DB value can never
   reach the renderer (same defence-in-depth the apply page applies).
</objective>

```typescript
// The branding contract THIS plan defines and 08-07 must satisfy.
export type BrandedCvBranding = {
  orgName: string
  primary: string | null            // raw DB value; safeHex'd inside
  secondary: string | null
  logo: { data: Uint8Array; format: 'png' | 'jpeg' } | null  // BYTES, never a URL
}
export function renderBrandedCv(
  data: BrandedCvData,
  branding: BrandedCvBranding,
): Promise<Buffer>
```

`logo` is BYTES by design: the renderer must never fetch a URL (SSRF + the
cold-start race in research Pitfall 4). The caller (08-07) downloads the object
from the private `org-logos` bucket under the tenant's own client.

react-pdf specifics worth knowing before writing the tree: `<View wrap={false}>`
keeps a work-history entry from splitting across a page break; `fixed` on a
`<View>` repeats it on every page (use for the footer); `render={({pageNumber,
totalPages}) => …}` on a `<Text>` produces page numbers; `<Image src={buffer}>`
accepts a Buffer/Uint8Array for PNG and JPEG only.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| candidate data → third-party client | The generated document leaves the agency; anything on it is disclosed |
| org branding values (DB) → renderer | Hex colours and logo bytes originate from user-editable settings |
| logo bytes → PDF image decoder | Attacker-influenceable binary is parsed by an image decoder inside the server function |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-17 | Information Disclosure | Rendered branded PDF | mitigate | Props typed `BrandedCvData` only (no contact/salary fields exist to render), plus raw-buffer absence assertions for email/phone/salary in the test |
| T-08-18 | Tampering | `brand_primary`/`brand_secondary` values | mitigate | `safeHex(value, BRAND_DEFAULTS.*)` at the top of the component — a rogue DB write falls back to the Altus default and never reaches the style object; pinned by the `'javascript:alert(1)'` test case |
| T-08-19 | Denial of Service | Image decoding of a malformed logo | mitigate | Logo bytes are already magic-byte-validated (08-03) and size-capped at 2 MiB by both the application and the bucket before they can ever be stored; the renderer only ever sees a stored object |
| T-08-20 | Denial of Service | Pathologically long candidate content | mitigate | Volume/length caps applied upstream in `toBrandedCvData` (08-03); the multi-page fixture pins that pagination works rather than looping |
| T-08-21 | Information Disclosure | Server-side fetch of a logo URL | mitigate | `BrandedCvBranding.logo` is `Uint8Array` bytes, never a URL — the template has no fetch path, closing SSRF by construction |
| T-08-SC | Tampering | npm/pip/cargo installs | mitigate | No installs in this plan; `@react-pdf/renderer` was gated and installed in 08-02 |
</threat_model>
