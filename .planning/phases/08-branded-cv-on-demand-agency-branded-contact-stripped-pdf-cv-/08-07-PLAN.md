<objective>
Wire the generation path: a Server Action that reads the candidate's current
data, renders the branded PDF in-process, stores it, and records exactly one
current branded copy — plus the candidate-page section and button that trigger
it.

Purpose: BCV-01 (on-demand only, never auto-on-parse — Phase 7 made parsed data
editable, so a copy generated at parse time would be stale the moment a field
is corrected), BCV-06 (regeneration supersedes cleanly), BCV-07 (zero AI spend).
Output: a working "Generate branded CV" control. Delivery (View/Download +
export audit) is deliberately the NEXT plan, so this plan never renders a link
to a route that does not exist yet.

## Two design rules taken straight from research

1. **Synchronous Server Action, NOT Inngest.** Every other multi-step candidate
   action in this codebase is async because it calls Claude/Voyage/Whisper.
   This one calls nothing — it is a deterministic template fill measured in
   hundreds of milliseconds. No polling UI, no "started" toast, no Inngest
   event (research Pitfall 7). The toast says "done" because it is done.
2. **Write-new-then-delete-old.** Upload the new PDF to a fresh path, point the
   row at it, and only then best-effort remove the previous object. A crash
   mid-regeneration must leave the OLD copy servable, never nothing (research
   Pitfall 6).

## Founder sign-off — NO ENTITLEMENT GATE (decided 2026-08-12)

Research recommended gating this action behind `requireEntitledOrg()` for
consistency with other mutations. **The founder OVERRODE that**: the action is
deliberately UNGATED by billing state. The reasoning is the stance already
documented on `cv-file/[cvId]/route.ts` — withholding a customer's own
candidate data behind a billing state is a data-hostage posture this product
does not take, and this action spends nothing (no AI, no third-party call) that
a billing gate would be protecting.

Authentication and RLS tenancy are UNCHANGED and remain the real gates. Do not
add `requireEntitledOrg()` back "for consistency"; if you find yourself
tempted, read the rationale comment this plan requires you to write.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser (any org member) → generation Server Action | A candidate id crosses from the client into a read-and-write path |
| candidate row (RLS) → PDF renderer → Storage | Tenant PII is transformed and written to a new persistent object |
| deployed code → not-yet-migrated database | Code can reach production before the founder's manual `db push` |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-38 | Information Disclosure | Cross-tenant candidate generation | mitigate | Candidate read is RLS-scoped under the caller's SSR client and returns the same "not found" for wrong-tenant and unknown; the org id comes from the authenticated profile, never from the request |
| T-08-39 | Elevation of Privilege | Non-entitled org performing a mutation | accept | Deliberately UNGATED by billing state (founder decision, 2026-08-12), matching the `cv-file` route's documented no-data-hostage stance. | T-08-40 | Tampering | Client-supplied storage path | mitigate | Path is composed server-side from the profile's org id, the validated candidate uuid and `crypto.randomUUID()`; no client string is ever concatenated into it |
| T-08-41 | Information Disclosure | PII in Sentry | mitigate | Error name + fixed subop + ids only; never the candidate name/email/phone or the storage path (which embeds neither, by construction, but is still withheld) |
