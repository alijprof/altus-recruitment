<objective>
Build the storage half of BCV-04: a shared org-logo helper (path convention,
signed-URL resolution, byte download) and the two Server Actions that upload
and remove a logo, with every gate the CV-upload path already learned to apply.

Purpose: the branded template needs logo BYTES from a tenant-safe place, and
the settings UI (08-06) and the public apply page need a URL for the same
object. Both consumers route through one helper so the path convention and the
legacy-URL precedence rule exist in exactly one file.
Output: `logo_storage_path` becomes the canonical logo pointer; the legacy
free-text `logo_url` survives only as a read-time fallback for orgs that pasted
a URL before Phase 8.

## The precedence rule this plan establishes (one place, one rule)

1. `logo_storage_path` set → the uploaded object is the logo (signed URL for
   display; bytes for the PDF).
2. else `logo_url` set → legacy external URL, DISPLAY ONLY. It is never
   fetched server-side (that would be an SSRF surface) and therefore never
   appears on a branded PDF; the settings UI (08-06) tells the owner to upload
   a file to get it onto branded CVs.
3. else → no logo; every consumer falls back to the org-name wordmark.

Uploading sets `logo_storage_path` AND clears `logo_url`, so an org can never
sit in a confusing "two logos" state.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser (any org member) → logo upload Server Action | Arbitrary bytes, an arbitrary MIME label and an arbitrary filename cross into Storage |
| Server Action → Supabase Storage (`org-logos`) | A write into a tenant-partitioned bucket |
| stored logo object → PDF image decoder | Bytes read back and parsed inside the server function |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-22 | Spoofing | `uploadOrgLogoAction` MIME handling | mitigate | `assertUploadableLogo` magic-byte check on the real bytes before any Storage call; `file.type` alone never decides |
| T-08-23 | Tampering | Path traversal via the uploaded filename | mitigate | Path is `{orgId}/logo-{crypto.randomUUID()}.{sniffed ext}` — the client filename is discarded entirely, never slugified-and-appended |
| T-08-24 | Elevation of Privilege | Non-owner editing org branding | mitigate | `users.role === 'owner'` check before any write, mirroring `updateBrandingAction`'s R8 ordering; RLS is the second gate |
| T-08-25 | Elevation of Privilege | Non-entitled org mutating settings | mitigate | `requireEntitledOrg()` gate, consistent with every other mutation in this codebase |
| T-08-26 | Denial of Service | Oversized upload exhausting the function | mitigate | 2 MiB cap checked before `arrayBuffer()`, plus the bucket's own `file_size_limit` as an independent server-side ceiling (08-01) |
| T-08-27 | Information Disclosure | Cross-tenant logo read/write | mitigate | Org id from the authenticated profile (never from the client) as the first path segment; `org-logos` Storage RLS enforces the same prefix independently |
| T-08-28 | Information Disclosure | SSRF via a legacy external `logo_url` | mitigate | Legacy URLs are DISPLAY-ONLY; `downloadOrgLogo` only ever reads from `logo_storage_path` inside our own bucket — no code path fetches a user-supplied URL server-side |
| T-08-29 | Information Disclosure | Signed logo URL leakage | mitigate | 1-hour TTL, minted per render on dynamic pages only; the bucket is private so the raw object URL is worthless |
| T-08-30 | Information Disclosure | PII/paths in Sentry | mitigate | Every capture is `new Error(name + fixed subop)` with org-id tags only — never the org name, path, or filename |
| T-08-31 | Repudiation | Orphaned or dangling logo objects | mitigate | Write-new-then-update-then-delete-old ordering; a failed row update removes the new object; a failed delete only leaves stale bytes that org-level erasure (08-08) still sweeps |
| T-08-SC | Tampering | npm/pip/cargo installs | mitigate | No installs in this plan |
</threat_model>
