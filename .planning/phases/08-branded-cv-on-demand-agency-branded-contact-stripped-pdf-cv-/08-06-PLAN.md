<objective>
Replace the URL-only logo field with a real upload widget on Settings →
Branding, delete the duplicate logo editor on the general Settings page, and
teach the public apply page the new precedence rule.

Purpose: research Pitfall 1 — `organizations.logo_url` is edited from TWO live
forms today (`/settings` from Phase 1, `/settings/branding` from Phase 5). If
only the branding page gains the upload flow, an owner can still paste a URL on
the general page and silently clobber the uploaded logo, defeating BCV-04
entirely. This plan makes `/settings/branding` the single canonical surface.
Output: one logo editor, one precedence rule, no way to end up with a broken
branded CV header.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser (owner) → branding Server Actions | File bytes and a remove command cross into org-level state |
| org logo value → public, unauthenticated apply page | A tenant-controlled value is rendered to anonymous visitors |
| two historical edit surfaces → one DB column | Divergent write paths to the same state |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-32 | Tampering | Duplicate `logo_url` writer on `/settings` | mitigate | Field, schema key and action patch entry all removed; source-inspection test pins zero occurrences in the stripped code of all three files |
| T-08-33 | Information Disclosure | Signed logo URL on a public page | mitigate | 1-hour TTL, `force-dynamic` render (no CDN/edge caching of the URL), private bucket so the underlying object is otherwise unreachable |
| T-08-34 | Tampering | XSS via a logo URL in `next/image` | mitigate | Uploaded logos produce URLs from our own Supabase Storage origin; legacy URLs retain the existing `https://`-prefix + 2048-char write validation and render in an `<img>` context only, never a script context |
| T-08-35 | Denial of Service | Apply page failing on a logo sign error | mitigate | `resolveOrgLogoUrl` returns `null` on any failure and the page falls back to the wordmark — an agency's inbound applications never break for a branding reason |
| T-08-36 | Elevation of Privilege | Non-owner uploading/removing a logo | mitigate | Server-side owner check in both actions (08-05); the widget's read-only state is UI convenience only |
| T-08-37 | Repudiation | Silent upload failure leaving the owner unsure | mitigate | Mandatory toast on every branch, no state cleared on failure, `router.refresh()` only after a confirmed success |
| T-08-SC | Tampering | npm/pip/cargo installs | mitigate | No installs in this plan |
</threat_model>
