<objective>
Write the two pure, dependency-free modules the rest of the phase composes:
the contact-stripping data mapper that turns a `candidates` row into exactly
what the branded template is allowed to see, and the PNG/JPEG magic-byte
sniffer that gates logo uploads.

Purpose: BCV-03's guarantee ("email, phone never render") is worth far more as
a TYPE-LEVEL property than as a rendering discipline — if `BrandedCvData` has
no `email` field, no future template edit can leak one. BCV-04's upload cannot
trust `file.type`, exactly as CV uploads learned not to (T-06-29).
Output: two modules with full unit coverage, importable from Server Actions,
route handlers and vitest with zero bundler magic.

## Locked scope decisions this mapper encodes

- **Stripped:** `email`, `phone`. These are the fee-protecting fields in the
  founder's locked decision.
- **Kept:** `location`. There is no literal `address` column in this schema;
  `location` is city/region ("Manchester, UK"), which is standard, expected
  content on a UK agency branded CV and is not a contact route (research
  Assumption A1, Reading B — pending founder confirmation).
- **Excluded (not an oversight — a deliberate allowlist):**
  `salary_current_estimate`, `salary_expectation`, `currency`. Salary
  expectation is commercially sensitive negotiating information and this
  document goes to the client (research Pitfall 5).
- **NOT scrubbed:** free text in `headline`/`about`. A regex scrubber's false
  positives mangle legitimate recruiter-authored content and its false
  negatives create false confidence. The module instead exports the UI warning
  string the Generate control shows.
</objective>

| `location` | `string \| null` | KEEP (A1 Reading B) |

| `salary_current_estimate`, `salary_expectation`, `currency` | — | EXCLUDE — absent from the output type |

The `Json` typing caveat is load-bearing: those two columns are `unknown` in
practice, populated by BOTH the CV parse path and the LinkedIn capture path
(migration 20260522094604). A row written by an older/newer code path can carry
a different shape, so the coercion must validate, never assume — the same
defensive posture `markCandidateFieldsFromCV` takes on the write side.

Magic bytes (dependency-free prefix match, mirroring `src/lib/cv/file-signature.ts`):
```
PNG  = 0x89 0x50 0x4e 0x47 0x0d 0x0a 0x1a 0x0a
JPEG = 0xff 0xd8 0xff
```

<task type="auto" tdd="true">
  <name>Task 2: PNG/JPEG magic-byte sniffer for logo uploads</name>
  <files>src/lib/upload/image-signature.ts, tests/unit/lib/upload/image-signature.test.ts</files>
  <behavior>
    - `sniffImageType` returns `'png'` for the 8-byte PNG signature, `'jpeg'` for the 3-byte JPEG signature, `'unknown'` for anything else including an empty buffer
    - An SVG document (`<svg …`), a GIF (`GIF89a`), a PDF (`%PDF-`), a WebP (`RIFF…WEBP`) and a Windows executable (`MZ`) all sniff as `'unknown'` and are rejected
    - `assertUploadableLogo` rejects a PNG-sniffing buffer declared as `image/jpeg` and vice versa (declared MIME must agree with the bytes)
    - `assertUploadableLogo` returns `{ ok: true, mime, ext }` with `ext` of `'png'` or `'jpg'` for an agreeing pair
    - A buffer larger than `MAX_LOGO_BYTES` (2 MiB) is rejected with `LOGO_TOO_LARGE_MESSAGE`
    - A truncated buffer shorter than the signature never throws — it returns `'unknown'`
    - Rejection messages are plain, user-facing, and mention PNG/JPEG (and that SVG is not supported for PDF rendering)
  </behavior>
  <action>
Create `src/lib/upload/image-signature.ts` mirroring the shape and discipline of
`src/lib/cv/file-signature.ts`: dependency-free, no `import 'server-only'`,
bounds-checked prefix matching that never throws, and a discriminated
`UploadableLogoCheck` result (`{ ok: true; mime: string; ext: 'png' | 'jpg' }`
or `{ ok: false; reason: 'wrong-format' | 'unsupported-format' | 'too-large'; message: string }`).

Export `MAX_LOGO_BYTES = 2 * 1024 * 1024`, `LOGO_WRONG_FORMAT_MESSAGE`,
`LOGO_UNSUPPORTED_FORMAT_MESSAGE`, `LOGO_TOO_LARGE_MESSAGE`, `sniffImageType`
and `assertUploadableLogo(bytes, declaredMime, byteLength)`.

Unlike the CV sniffer, do NOT search a window for the signature — an image
header is at offset 0 or the file is not the image it claims to be. Header
comment must record WHY SVG is refused: `@react-pdf/renderer`'s `Image` accepts
JPG/PNG/Buffer only and has no SVG rasterisation, so an accepted SVG would
render on the apply page but silently vanish from the branded PDF (research
Pitfall 2). Deliberately a separate module rather than an extension of the CV
sniffer — the CV module's contract is PDF/DOCX for the parse pipeline, and
merging the two would couple a customer-facing upload gate to the parse gate.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| database jsonb (`work_experience`, `education`) → PDF renderer | Untyped, multi-writer data crosses into a document-generation engine |
| uploaded file bytes → application | Client-supplied bytes and a client-supplied MIME label enter the system |
| candidate PII → client-facing document | The branded PDF leaves the agency and reaches a third party |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-11 | Information Disclosure | `toBrandedCvData` output | mitigate | `BrandedCvData` has no `email`/`phone`/salary keys, so the template physically cannot render them; pinned by `@ts-expect-error` compile assertions plus a full-serialisation runtime test |
| T-08-12 | Tampering | Malformed/hostile jsonb in `work_experience`/`education` | mitigate | Defensive coercion with per-field type checks, explicit literal-key object construction (no spread), and volume/length caps; never throws |
| T-08-13 | Denial of Service | Unbounded jsonb content inflating the PDF | mitigate | Hard caps: 20 work entries, 12 education entries, 60 skills, 12 sector tags, per-string truncation |
| T-08-14 | Spoofing | Logo upload declaring a false MIME type | mitigate | `assertUploadableLogo` sniffs magic bytes and requires the declared MIME to agree; `file.type` is never trusted alone (same class as T-06-29 for CVs) |
| T-08-15 | Tampering | Polyglot/dangerous payload uploaded as a logo (SVG with script, EXE, PDF) | mitigate | Strict offset-0 allowlist of PNG and JPEG only; everything else is `'unknown'` and rejected before any Storage write (enforced in 08-05) |
| T-08-16 | Information Disclosure | Contact details embedded in free-text `about`/`headline` | accept | Documented limitation: no regex scrubbing (false positives mangle real content, false negatives create false confidence). Mitigated by `BRANDED_CV_FREE_TEXT_WARNING` shown at the Generate control and by recruiter review before sending |
| T-08-SC | Tampering | npm/pip/cargo installs | mitigate | No installs in this plan — both modules are dependency-free by design |
