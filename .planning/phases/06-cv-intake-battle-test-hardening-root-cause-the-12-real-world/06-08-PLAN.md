<objective>
Move Tier-2 rejection as early as each path architecturally allows.

The recruiter path can reject at upload: the Server Action holds the actual bytes
before anything is written. The apply path cannot — the browser PUTs straight to
Storage via a signed URL and the server never sees the bytes at submit time. But
it CAN sniff immediately after, inside `confirmApplyAction`, which already reads
Storage to verify the object exists. That is the earliest honest point on that
path, and this plan implements it rather than pretending the two paths are the
same.

Purpose: `file.type` is browser-derived from the extension. Renaming `cv.docx` to
`cv.pdf` sails through today's `ACCEPTED_CV_MIME` check and fails three minutes
later with a generic message and a doomed retry button.

Output: a dependency-free signature module and both call sites.
</objective>

<interfaces>
<!-- File signatures. Stable, short, and a dependency here buys nothing. -->
```
PDF   : 25 50 44 46 2D              "%PDF-"
ZIP   : 50 4B 03 04                 "PK\x03\x04"  (docx/xlsx/pptx/odt/jar/plain zip)
OLE2  : D0 CF 11 E0 A1 B1 1A E1     legacy .doc / .xls / .ppt
RTF   : 7B 5C 72 74 66              "{\rtf"
```
Distinguishing a DOCX from any other ZIP: the archive must contain the entries
`[Content_Types].xml` AND `word/document.xml`. An ODT instead carries a `mimetype`
entry of `application/vnd.oasis.opendocument.text`.

**Do NOT import jszip in production code.** It is a devDependency only (plan
06-01), and promoting it to a runtime dependency for this check is unjustified.
ZIP stores entry FILENAMES uncompressed in both the local file headers and the
central directory, so a plain byte-scan of the buffer for the ASCII sequences
`[Content_Types].xml` and `word/document.xml` is sufficient and correct for the
Tier-2 goal (separating a real DOCX from an ODT or a renamed archive). Document
that reasoning in the module header, including its known limit: it is a
positive-signal check, not a full ZIP parse.

**Recruiter path** (`src/app/(app)/candidates/[id]/actions.ts`, `uploadCVAction`):
validation order is already "cheapest first" — `ACCEPTED_CV_MIME.has(file.type)`,
then `file.size > MAX_CV_BYTES` (10 MiB), then `requireEntitledOrg()`, then
`nextCVVersion`, then `supabase.storage.from('cvs').upload(...)`, then
`createCandidateCV`, with a Storage rollback if the row insert fails.
The byte sniff belongs AFTER the size cap (so a 10 MiB read is bounded) and
BEFORE the entitlement gate and any Storage write.
`slugifyFilename` (path-traversal defence) and the `${organizationId}/${candidateId}/`
storage path layout must not change — `parse-cv.ts`'s tenant check depends on
that layout.

**Apply path** (`src/app/(public)/apply/[orgSlug]/actions.ts`):
`submitApplyAction` validates a CLIENT-SUPPLIED `fileMeta` (`name`, `size` ≤
`MAX_BYTES` 10 MiB, `type` ∈ `ALLOWED_MIMES`) and issues a signed upload URL —
the server never sees bytes here. `confirmApplyAction` then:
0. re-derives the org from the slug (the only trusted tenancy signal),
1. re-verifies the CV row belongs to that (org, candidate),
2. verifies the Storage object exists via `storage.from('cvs').list(dir, {search: basename, limit: 1})`,
2b. checks `isOrgEntitled` (fails closed; keeps the candidate, skips AI),
3. fires `inngest.send('cv/uploaded')`, marking the row failed with
   `CV_STUCK_MESSAGE` if the send throws.
The new sniff slots in as **step 2c**, between the existence check and the
entitlement gate.
Precedent for refusing at confirm time while keeping the stored rows: the
existing `objectExists === false` branch returns
`{ ok: false, formError: 'CV upload did not complete. Please try again.' }`.

Message literals to reuse (added in plan 06-07, do not invent new copy):
`CV_WRONG_FORMAT_MESSAGE` (substring `isn’t a PDF or Word`),
`CV_UNSUPPORTED_FORMAT_MESSAGE` (substring `only PDF and Word`),
`CV_DAMAGED_FILE_MESSAGE` (substring `appears to be damaged`).

Corpus fixtures that make this testable (plan 06-03):
`tier2/t2-docx-renamed.pdf`, `tier2/t2-pdf-renamed.docx`, `tier2/t2-legacy.doc`,
`tier2/t2-plain.rtf`, `tier2/t2-opendocument.odt`, `tier2/t2-zero-byte.pdf`,
`tier2/t2-pdf-corrupt.pdf`, plus every `tier1/` fixture as the positive control.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `uploadCVAction` | `file.type` is client-supplied and spoofable |
| browser → Storage (signed URL) | Bytes reach Storage without ever passing through the server |
| browser → `confirmApplyAction` | An unauthenticated public endpoint drives a service-role read |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-29 | Spoofing | content-type spoofing on both upload paths (ASVS V12) | mitigate | `assertUploadableCV` decides from raw bytes, never from `file.type`; the recruiter path rejects before any write, the apply path at the first server-visible moment |
| T-06-30 | Denial of Service | 10 MiB reads on a public endpoint | mitigate | Ranged head read preferred (64 KiB); full download only as a fallback and only under the pre-existing 10 MiB cap; `isDocxArchive` scans at most the first and last 64 KiB |
| T-06-31 | Denial of Service | zip bomb labelled `.docx` | mitigate | Never inflated — only entry NAMES are byte-scanned; nothing in the production path calls a ZIP decoder |
| T-06-32 | Tampering | forged `candidateCvId` at confirm | accept (already mitigated) | The existing org-from-slug re-derivation plus the (org, candidate) re-verification are untouched by this plan |
| T-06-33 | Elevation of Privilege | jszip entering the runtime bundle | mitigate | Hand-rolled byte scan; enforced by a `grep` gate over `src/` in Task 1's verify |
| T-06-34 | Denial of Service | false rejection of a legitimate CV | mitigate | Ranged-read ambiguity is treated as INCONCLUSIVE and allowed through; only positive contradictions reject |
</threat_model>
