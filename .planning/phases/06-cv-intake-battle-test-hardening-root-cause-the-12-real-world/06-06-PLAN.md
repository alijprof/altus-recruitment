<objective>
Close the gap between what TypeScript asserts (`as ParsedCV`, `as number`,
`as string[]`) and what actually arrives from a probabilistic model, and close the
gap between what JavaScript considers a valid string and what Postgres will
accept. Two choke points, both proven by 06-RESEARCH.md to cover all six classes:

1. A zod coercion boundary in `parseCV()` — every consumer (`parse-cv.ts`,
   `reconcile-cv-parses.ts`, `acceptCVFieldsAction`) inherits the fix at once.

   `markCandidateFieldsFromCV` — the last shared choke point before the database.

Sanitisation alone fixes classes 1 and 4 only; coercion alone fixes classes 3, 4
and 5 only. Both ship together or the phase does not close (Pitfall 2).

Purpose: turn the entire layer-2 RED suite green without weakening a single
assertion or breaking a single negative control.

Output: two new pure modules, their unit tests, and the wiring into the three
production files.

<!-- Column types the coercion bounds are derived from
     (migration 20260513152244, verified by local schema introspection): -->
```
candidates.salary_current_estimate : integer  (int4, max 2147483647)
candidates.salary_expectation      : integer
candidates.years_experience        : numeric(4,1)   -> |v| must be < 1000
candidates.skills, sector_tags     : text[] not null default '{}'
candidates.work_experience, education : jsonb
candidate_cvs.extracted_data       : jsonb
```

Only TWO things are illegal for Postgres in this pipeline (verified against
Postgres 17.6 + PostgREST v14.5, 2026-08-09):
```
U+0000                -> 22P05 "unsupported Unicode escape sequence"
lone UTF-16 surrogate -> PGRST102 "Empty or invalid json" (PostgREST layer)
```
Everything else — `U+0001`–`U+001F`, emoji, ZWJ, RTL, astral plane, BOM, soft
hyphen, 1.1 MB values — is legal and MUST be preserved. This is a CV; the content
is the product. Stripping "control characters" wholesale is an anti-pattern.

Lone-surrogate regex (ES2018 lookbehind, verified on Node 24):
`/[\uD800-\uDBFF](?![\uDC00-\uDFFF])|(?<![\uD800-\uDBFF])[\uDC00-\uDFFF]/g`

Existing code to be replaced:
- `src/lib/ai/claude.ts:337` — `return toolUse.input as ParsedCV`
- `src/lib/ai/claude.ts:273` — `years_experience_total: { type: 'number' }`
  (no description, no bounds — the weakest-specified field in the whole tool, and
  the most likely source of a calendar-year mis-read)
- `src/lib/db/candidate-cvs.ts:286-307` — `toParsedCVSubset`'s six `as` casts
- `src/lib/ai/cv-extract.ts:26-31` — `normaliseWhitespace`, correct for
  whitespace, silent on NUL

`markCandidateFieldsFromCV` crash sites (both throw UNCAUGHT today):
`candidate-cvs.ts:440` `(args.parsed.name ?? '').trim()` and
`candidate-cvs.ts:317` `(item.role ?? '').trim()` on a null array element.

`DbResult` failure shape and its callers: `{ ok: false, code: 'not_found' | 'internal' | 'duplicate' }`.
Widening it with an OPTIONAL `detail?: string` is additive — no existing caller
needs to change.

PII rule for `detail` (ASVS V7): store `${err.code}` plus the column/subop name
ONLY. NEVER `err.message` — PostgREST echoes the offending value
(`invalid input syntax for type integer: "£45,000"`), and a NUL-bearing name
would be worse.

Anti-pattern to avoid: `z.coerce.number()` without `.catch()` — a throw there
converts one bad field into a whole-parse failure, trading one Tier-3 bug for
another.
