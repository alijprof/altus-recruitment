<interfaces>
<!-- Facts that make the retry safe and interpretable. -->

The retry path already exists and is the ONLY write this plan performs against
the customer org: `retryParseAction` resets the row to `parsing_status='pending'`
with `parse_error` and `parse_error_detail` cleared, then re-dispatches
`cv/uploaded`. It re-parses the customer's OWN already-stored file. It creates no
new data of any kind; at worst it re-runs a parse the customer already paid for.

`markCandidateFieldsFromCV` enforces D-08: it ONLY fills fields that are currently
empty. A successful retry therefore cannot overwrite anything a recruiter typed.

06-RESEARCH.md Pitfall 3 — do not accept a false green. The retry calls Haiku
again, and Haiku is non-deterministic. A row could go green because the model
happened to return `24` instead of `2015`, with the defect untouched. Acceptance
is gated on the deterministic layer-2 suite (already green, plan 06-09); the 12
retries are the CUSTOMER-FACING confirmation. Record, per file, which fix class
the forensic replay said it exercised, so a green result can be attributed rather
than assumed.

Migrations whose production status must be stated in the handoff (research open
question 5 — present in the local stack, believed unapplied in production, with
three later migrations sitting behind the first):
```
20260804120000  candidate_cvs.parse_error_detail
20260804120100  (follow-on)
20260804130000  set_created_by trigger
20260804130100  (follow-on)
20260804140000  record_audit dedupe
```
This phase adds NO migration and is correct whether or not these are applied —
`updateCandidateCVParse` retries without `parse_error_detail` on a `PGRST204`.
But `parse_error_detail` is where this phase's new root-cause strings LAND, so
until `20260804120000` is applied, the improved diagnostics are written and
discarded. That is the founder's call to make with full information.

Known operational caution (2026-07-08): applying a migration through the Supabase
MCP `apply_migration` stamps the ledger version as the CURRENT UTC timestamp
rather than the filename's, which makes a later `db push` drift. Migrations should
go through the founder's `db push` script.

The reconciler (`reconcile-cv-parses.ts`) sweeps stuck `pending` rows and
auto-resumes budget-parked `failed` rows via the `%AI budget%` ilike — it will not
touch honestly-failed rows, so a retry that fails again stays visible rather than
being silently churned.
