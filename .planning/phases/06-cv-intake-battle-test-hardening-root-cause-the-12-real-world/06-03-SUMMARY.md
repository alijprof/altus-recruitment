## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `pnpm fixtures:regen` was not actually idempotent — Chromium PDF dates**
- **Found during:** Task 1, self-imposed idempotency check (not in the plan's automated verify gate, but required by the plan's `<verification>` section: "running it twice leaves `git status` clean")
- **Issue:** Playwright's `page.pdf()` embeds the real wall-clock time in `/CreationDate` and `/ModDate` on every render. Running the generator twice in a row produced byte-different PDFs every time.
- **Fix:** Added `stabilisePdfDates()` — a same-length regex substitution (`(D:YYYYMMDDHHMMSS+00'00')` → a fixed constant) applied to every Playwright-rendered PDF buffer before it's used for anything else. Same-length replacement preserves every downstream xref byte offset, so no need to rebuild the file.
- **Files modified:** tests/fixtures/cv-corpus/generate.mjs
- **Verification:** 5 consecutive `node generate.mjs` runs produced byte-identical `md5sum` output for every PDF fixture.
- **Committed in:** df0f708 (Task 1 commit)

**2. [Rule 1 - Bug] `pnpm fixtures:regen` was not actually idempotent — jszip auto-created folder dates**
- **Found during:** Task 1, same idempotency check, after fix #1 above (DOCX fixtures were STILL flaky across consecutive runs even with every explicit `zip.file()` call passing a fixed `date` option)
- **Issue:** jszip auto-creates parent-directory entries (e.g. `_rels/`, `word/`) for nested file paths. These synthetic directory entries never go through an explicit `zip.file(path, content, options)` call, so they get stamped with `new Date()` at generation time regardless of what every real file entry was told.
- **Fix:** Added `stabiliseZipFolderDates()`, which force-sets `.date` on every entry in `zip.files` (files AND auto-created folders) immediately before `generateAsync()`.
- **Files modified:** tests/fixtures/cv-corpus/generate.mjs
- **Verification:** 5 consecutive runs produced byte-identical `md5sum` output for every DOCX fixture; full-corpus `git diff --stat` empty across two consecutive full regenerations.
- **Committed in:** df0f708 (Task 1 commit)

**3. [Rule 1 - Bug] Buffer detachment silently zeroed a PDF's reported byte length**
- **Found during:** Task 1, while prototyping the long-40-pages fixture (`bytes= 0` printed despite a successful, non-empty render)
- **Issue:** unpdf/pdf.js can neuter/detach the underlying `ArrayBuffer` it is handed. Extracting text from a `Uint8Array` VIEW over a buffer still needed afterwards (e.g. to write to disk or report its length) silently zeroed that buffer's `.length` once pdf.js finished with it.
- **Fix:** Every place that hands bytes to `getDocumentProxy` (the production-mirror `mirrorExtractTextFromBuffer`, and `renderPdfFromHtml`'s date-stabilisation return path) now copies into a fresh `Uint8Array`/`Buffer` first, never passing a view over memory still owned elsewhere.
- **Files modified:** tests/fixtures/cv-corpus/generate.mjs
- **Verification:** Re-ran the long-40-pages generation; byte length reported correctly (67,639 bytes) both before and after self-check extraction.
- **Committed in:** df0f708 (Task 1 commit)

**4. [Rule 1 - Bug] Own text-generation process embedded raw NUL bytes while prototyping, instead of visible escape-sequence text**
- **Found during:** Task 1/2 prototyping, mirroring the exact failure mode documented in plan 06-01's SUMMARY
- **Issue:** While drafting a throwaway prototype script referencing "a NUL character" conceptually, my own output embedded 3 literal `0x00` bytes into the `.mjs` source text instead of the 6-character visible text I intended, causing `file`/`grep` to classify the script as binary `data`.
- **Fix:** Deleted the corrupted prototype and rewrote using `String.fromCharCode(0)` everywhere a NUL character is conceptually needed in source code — unambiguous plain-ASCII source, impossible to accidentally emit as a raw byte. Applied this pattern throughout the final committed `generate.mjs` (`NUL_CHAR = String.fromCharCode(0)`), and verified zero raw NUL bytes in every committed source file (`.mjs`/`.md`/`.json`/`.html`) via a byte-level Python scan before each commit.
- **Files modified:** none in the final commit (caught and fixed entirely during prototyping, before any commit)
- **Committed in:** N/A (prevented, not present in any commit)

**5. [Rule 3 - Blocking] ESLint unused-variable warning cleanup**
- **Found during:** Task 2, pre-commit `pnpm lint` check
- **Issue:** An unused `copyFileSync` import (Task 1) and an unused `_browser` parameter on `buildHostile()` (Task 2, since no hostile fixture needs Playwright) each produced a lint warning.
- **Fix:** Removed the unused import; removed the unused parameter (and the corresponding argument at the call site) rather than relying on the underscore-prefix convention, since it genuinely isn't needed.
- **Files modified:** tests/fixtures/cv-corpus/generate.mjs
- **Verification:** `pnpm lint` reports 0 warnings/errors attributable to `generate.mjs`.
- **Committed in:** df0f708, 3967bf1

## Issues Encountered
- The plan's `<interfaces>` PDF ToUnicode-CMap recipe example used a composite `/Type0`/`Identity-H` font in its illustrative snippet's surrounding context; a literal Identity-H implementation garbled the extracted text (2-byte CID interpretation mismatched against the 1-byte codespace CMap). Switched to a simple `/Type1 /Helvetica` font with `/WinAnsiEncoding` plus the same `/ToUnicode` CMap, exactly matching the plan's literal PDF object snippet — confirmed via generation-time self-check that this reproduces the documented `" BCDEF  BCDEF"` result precisely.
- Confirmed empirically (not assumed) that `t2-pdf-renamed.docx`'s thrown error has `.name === 'Error'` (jszip's generic error class, not a more specific named exception) — recorded as observed rather than second-guessed.
